环保院的工艺组在给市政污水厂选活性污泥参数时，反复要解同一类稳态问题：单级完全混合反应器（CSTR）里，微生物按 Monod 动力学吃掉进水基质，问最终出水基质浓度和污泥浓度稳定在哪里、稀释率再往上抬会不会把菌种直接冲走。这套判断现在散在几个人的电子表格和手算里，口径经常对不齐。请把它做成一个常驻的稳态求解后端，让上游的设计程序把一组工艺参数丢过来、拿回一份可复核的稳态解，而不是每次现推公式。

核心是这样一套物料衡算与动力学的联立求解。进水基质浓度 S0、稀释率 D（进水流量除以反应器体积）、最大比增长速率 μmax、半饱和常数 Ks、产率系数 Y 是输入。比增长速率随基质变化，遵循 μ = μmax·S/(Ks+S)。系统达到稳态时，微生物的净增长恰好被出流带走，于是 D = μ，反解出稳态出水基质 S = Ks·D/(μmax − D)，污泥浓度 X = Y·(S0 − S)。这里藏着一个必须守住的物理边界：当稀释率 D 追平或超过 μmax，菌种来不及繁殖就被冲光，进入冲刷状态，此时污泥浓度归零、出水基质等于进水（X = 0，S = S0），绝不允许把它继续代进上面那个分式算出负的分母或负的污泥量。同理，若在未冲刷区解出的 S 反而不小于 S0，也说明工况落在了冲刷边界之外，一律按冲刷处理。求解器要能自己识别自己处在哪个区段，并把「是否冲刷」作为结果的一部分明确回报。

服务要能接住成规模的工况扫描，而不只是单点求解。除了给定一组参数求一个稳态解，还要支持沿稀释率做区间扫描：给定 D 的起止与步长，返回一串 (D, S, X, μ, 是否冲刷) 的点列，让设计者一眼看到污泥浓度随稀释率上升而下滑、并在跨过 μmax 时跌到零的整个过程。参数的合法性要认真把关：D、μmax、Ks、Y 任一非正，S0 为负，都属于无效工况，要返回带明确原因的结构化错误而不是算出一个看似正常其实无意义的数。工况参数要能以具名档案的形式登记留存、之后凭名字取回复算，服务内置一份可手工核对的示范档（一组 D 明显小于 μmax、能解出正污泥浓度的有氧工况），保证任何人拉起服务就能立刻验证算得对不对。多个工况档同时在算时，各自的结果只归属到自己的名下，不允许并发请求之间互相串改数据。

有几条关系必须始终成立，请用自动化测试把它们钉死：在未冲刷区只抬高稀释率 D，稳态出水基质随之升高、污泥浓度随之下降；无衰减项时只把进水基质 S0 加倍，污泥浓度近似翻倍，而稳态出水基质由 D 决定、与 S0 无关；一旦 D 越过 μmax，污泥浓度必须干净地跌到零而不是变成负数；D 恰好等于 μmax 这个临界点要有专门处理，不能让分母为零。测试要同时覆盖正常工况、边界工况和这几条交叉关系。

实现选用 FastAPI，运行在 Python 3.12 上，按职责把动力学内核、稳态求解、参数档管理、HTTP 接口与持久化分成互相独立的模块，避免把全部逻辑压进一个文件。数据落在容器内的轻量数据库即可。请随仓提供 Dockerfile，使镜像构建完成后容器一跑起来服务即对外可用，并把上述稳态解、区间扫描、冲刷判定、非法输入拒绝与并发隔离都用测试固定下来。范围就限定在这套稳态核算本身，仅通过 HTTP 对外提供能力，不需要网页界面，也不涉及排污审批、污水厂工单或任何账户体系。
